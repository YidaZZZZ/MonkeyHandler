# 治理 Prompt

> **状态：已审核（2026-09-30 批准）**。落点：执行闭环周期结算（M3）、双周复盘、synthesis/ 审核门。

## P-GOV-1 周期结算三栏

**目的**：阻断 R4 指标替代回路，把「成功」拆为多维（守护 F26/F30）。
**来源**：thinking-in-systems（指标替代与延迟、Goodhart/Campbell 定律）、understanding-by-design（进度≠掌握）。

```text
每个训练周期结束时，产出三栏结算：
① 主指标：能力证据达成度（期末测评结果、动作/成绩进步）——不是打卡数；
② 反指标：同期内的错误率、投诉/困扰反馈、退出倾向、疲劳信号（睡眠侵蚀、
   RPE 持续走高）、打卡与测评的背离度（打卡上升但测评停滞 = 空心依从告警）；
③ 停止条件核对：预设的停止条件是否触发（如连续两周反指标恶化）？
   触发即冻结加量并复盘，禁止「继续优化」。
```

## P-GOV-2 偏差类干预随访

**目的**：阻断 R6 新鲜感误判回路（守护 F30）。
**来源**：misbehaving（偏差是情境产物；把 A/B 异常当理论机会）、thinking-fast-and-slow（归因纪律）。

```text
对任何新上线的动机/行为机制：
- 设定 4-6 周随访窗口；上线初期的提升一律标记为「含新鲜感效应，不可归因」；
- 随访判定：效果衰减 >50% → 停止归因并下线或重设计；效果稳定 → 记录为
  持续有效；效果反转（损害主指标或反指标）→ 立即下线；
- 对照要求：无法随机对照时，用中断时间序列或前后对照，并如实标注不可
  识别之处；证据不足时缩小实验范围而非扩大推广。
```

## P-GOV-3 双周复盘

**目的**：把前后台责任与延迟副作用纳入常规检查（守护 F30、F28）。
**来源**：this-is-service-design-doing（前台体验与后台履约一致）、thinking-in-systems（延迟与杠杆点）。

```text
每两周复盘，固定五问：
1. 哪些指标提升了？归因证据是否充分（过 P-GOV-2 标准）？
2. 哪些用户体验群体受损了？（含少数派：低依从者、恢复受限者）
3. 哪些退出路径被加长或变难了？
4. 哪些承诺缺少后台履约支撑（承诺-履约对齐检查）？
5. 哪些证据仍然不足？→ 不足处缩小动作，不扩大投入。
输出：一页复盘记录，进入下一周期计划输入。
```

## P-GOV-4 审核门（synthesis/ 入库检查）

**目的**：守护 F29 知识纪律与 F28 信任——未经审核的提示词/机制不进运行时；审核门是唯一闸门。
**来源**：humanity 流水线规范。

```text
synthesis/ 新内容入库前逐项核对：
1. 溯源完整：每条主张可追溯到 works/ 中对应著作的 verification.md「入库」清单；
2. 验证状态：所引主张未被改判「存疑/被推翻」；若已改判，引用它的 prompt 同步失效待审；
3. 标注完整：条目是否附有风险信息标注（争议、滥用可能、证据边界）——缺失则补齐后再审；
4. 用户审核：条目标注审核人（用户）与审核日期，状态从「已审核（2026-09-30 创始人批准）」改「已审核」；
5. 版本记录：变更历史与理由留痕。
任何一项不满足 → 保持草稿状态，不得被 core/humanity.py 加载。
```

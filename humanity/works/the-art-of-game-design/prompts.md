# 全景探秘游戏设计艺术 —— 提取的提示词与方法论

> 流水线第④步产出。核心目标：理解人类 → 理解用户 → 让用户痴迷训练。
> **状态：全部「已审核（2026-09-30 创始人批准）」**——提取不做事前排除，去留由用户在审核门逐案决定。

## 提示词

### P1 目标体验陈述提示词（服务：痴迷训练）
「每期训练计划生成前，先用一句话陈述本期的目标体验（『用户练完这期应感到______』）；每次迭代修订时自问：这次修改让用户离该体验更近了吗？不以功能或内容量回答。」
- 出处：主张 1（设计体验）+ 主张 3（迭代）
- 落点：`domains/*/plan.py` 计划 rationale 字段；M3 再校准的评审问题

### P2 三透镜自检提示词（服务：痴迷训练）
「对每次训练过三问（限用透镜子集，防堆砌）：① 目标透镜——用户能一句话说出本次目标吗？② 反馈透镜——动作完成后多久、以何种信号知道结果？③ 难度透镜——挑战相对当前能力是过高/过低/平衡？任一问答案为否，修改计划而非修改用户。」
- 出处：主张 2（透镜法）+ 主张 4（心流操作化）
- 落点：`domains/*/plan.py` 计划生成约束；与《心流》P2 训练节次三问衔接

### P3 兴趣曲线检查提示词（服务：痴迷训练）
「检查本期计划的强度结构：是否有开场引导、中期高潮（新动作/新目标/测试日）与必要低谷（恢复/技术打磨）？全程平直或全程高强度均须重排。本结构为经验假设，须用完成率与自报疲劳校准，不作为硬定律。」
- 出处：主张 5（兴趣曲线，存疑标注：经验法则）
- 落点：`domains/*/plan.py` 周期排程；`core/motivation.py` 难度校准输入

### P4 外在奖励审计提示词（服务：痴迷训练）
「审计本设计中的外部奖励（徽章/积分/里程碑）：它是否可能把『为成长而练』改写为『为奖励而练』？是否监控了奖励撤除后行为是否保留？外部奖励只作行为锚点，不作核心动机来源。」
- 出处：主张 7（外在奖励内在化风险，方向性部分）
- 落点：`core/motivation.py` 动机设计的奖励审计规则；与《心流》自成目标方向对读

### P5 紧迫与稀缺结构提示词（服务：痴迷训练）
「紧迫与稀缺结构（限时挑战、阶段倒计时、限量化挑战）作为可选设计元素入库（状态：已审核（2026-09-30 批准））：默认优先使用真实时间结构（真实周期截止、真实阶段更替）；若采用呈现层紧迫手法，须在条目 rationale 标注『紧迫来源为设计而非真实约束』，并跟踪其对完成质量、疲劳与退出的影响。」
- 出处：主张 5（兴趣曲线）+ 主张 6（平衡性）的使用面扩展
- 状态：已审核（2026-09-30 批准）
- 落点：`domains/*/plan.py` 周期排程选项；`core/motivation.py`

## 方法论

### M1 计划即原型的迭代闭环（服务：痴迷训练）
每期训练计划按「实验假设」对待：预设可观测指标（完成率、RPE 分布、自报评分、中断点），期中/期末回看并修订下一版。第一版计划几乎必错——迭代节奏优先于初始完美。
- 出处：主张 3（原型-测试-迭代）
- 落点：M3 执行与再校准的周期结算流程

### M2 参数平衡方法论（服务：痴迷训练）
训练的难度、容量、动作选择构成参数空间；平衡目标不是唯一最优解，而是保持「多个有效选择」：按用户状态在相邻难度档位间留出真实选择余地，用迭代测试而非一次性计算定参。
- 出处：主张 6（平衡性）
- 落点：`core/motivation.py` 的 `adjust_difficulty`；`domains/*/plan.py` 动作变体设计

### M3 透镜子集与反堆砌规则（服务：理解人类）
透镜/清单只取与训练设计直接相关的有限子集（目标、反馈、难度、体验陈述），且每条须产生一个可执行修改；「为完整性而添加的检查项」一律移除——防功能主义堆砌与菜单式套用。
- 出处：主张 2（透镜法的使用边界）
- 落点：`core/humanity.py` 知识库组织规则（入库提示词的数量与来源控制）
